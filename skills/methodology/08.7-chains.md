# Session 08.7: Chains and Workflows

## Objective

Prove what the category sessions could only hypothesise. A category session
resolves one narrow claim at a time and stops. Real damage usually needs two
or three of those claims joined: a mass-assignment field that sets a role,
then an admin export; a workflow skip that marks an order paid, then a
storage read of the fulfilled file. This session joins them, end to end, in
the sandbox, so the final report separates observed paths from hypothetical
ones honestly and severity rests on what was actually achieved.

This session runs only when the environment is `sandbox`. On staging or with
no live target it is `blocked` with reason "requires sandbox", and every
chain is reported as a risk scenario with its observed and unobserved edges
marked.

## Preflight

- Read every session report from 02 to 08.5: the `likely` findings, the
  unresolved candidates, the candidate index rows marked "chain" or
  "workflow", and the tested defenses.
- Read `01-recon/sandbox.md`. Confirm the isolation check still passes and
  the reset command works. Reset before the first chain.
- Confirm the synthetic fixtures cover every identity and object state the
  chains need. Seed more if not. Never introduce real data to make a chain
  possible.

## Chain candidates

Write a table, one row per chain. If the table is empty after an honest
pass, the session is `not_applicable` with that table as the evidence.

| Chain | Goal | Edges (in order) | Edge evidence so far | Fixtures needed |
|-------|------|------------------|----------------------|-----------------|

A goal is a concrete outcome on synthetic data: read tenant B's invoice as
tenant A's ordinary user; obtain the administrator role from a self-service
signup; make the owner pay for an operation without authenticating; alter a
fulfilled order's amount. An edge is one narrow claim from a category session
or one workflow transition from Session 04. Prefer chains whose edges are
already `likely` or `confirmed`; chains built from `insufficient` edges are
speculation and stay out of the table.

## Controlled validation

For each chain:

1. Reset the sandbox and record the reset.
2. Run the chain as one continuous transcript under one identity, from the
   starting state to the goal. Each edge keeps the baseline, probe, control
   discipline: the legitimate path is the positive control, and a fixture in
   the wrong state or tenant is the negative control.
3. At every edge record the request, the response, and the resulting
   persistent state (a database row, an object listing, a role claim) with
   `ensphere evidence log`, one evidence ID per edge.
4. A chain is **observed** only when every edge succeeded in that one run and
   the goal state is recorded. If an edge fails, record which control stopped
   it; that is a tested defense, and the chain is a risk scenario up to that
   edge.
5. Reset the sandbox before the next chain. Chains never share state.

Keep going until the chain is observed or an edge is contradicted. Do not
add edges that the sandbox cannot support, and do not substitute a different
goal mid-run; a new goal is a new row.

## Resolution

- An observed chain promotes each `likely` edge it used to `confirmed` with
  `direct` evidence, and becomes its own finding of kind `vulnerability`
  whose observed facts are the edge evidence IDs in order.
- A chain broken at edge N produces a tested-defense entry for the control
  that broke it and leaves the earlier edges at their existing status.
- Severity comes from the goal reached on synthetic data, described as what it
  would reach on real data. Do not inflate a chain that ends short of its
  goal.

## Stop rules

- Only the sandbox and its stubs. A chain that would need staging, a real
  third-party account, or production configuration stops at that edge and is
  reported as a risk scenario from there.
- No real data, no real secrets, no persistence beyond the run, no changes
  outside the sandbox.
- Stop when the candidate table is exhausted. Do not invent goals to fill it.

## Report

Write `08.7-chains/report.md` with: the sandbox record and reset log; the
chain table with each chain marked observed, broken at edge N, or not run;
one section per observed chain with the ordered edge evidence, resulting
state, root causes, and the single fix that breaks the chain earliest; tested
defenses; risk scenarios with unobserved edges marked; Needs from you.
