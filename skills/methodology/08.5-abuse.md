# Session 08.5: Abuse and Cost Controls

## Objective

Find every place where an attacker can make the system do expensive work,
consume storage or bandwidth, or run up a bill without a control stopping
them. Report each as a `missing_control` finding with the concrete limiter or
cap to add. Verify that the controls the project already has actually engage.

This session runs for every target with a server component. It always loads
`checklists/abuse-and-cost.md` plus the stack checklists assigned by the plan.

## Preflight

- Read the recon stack table, the billing-exposed services list, the storage
  and files inventory, and the "rate and cost controls already present" table.
- In a sandbox, choose the burst count and window per endpoint yourself,
  starting below the documented or expected limit. On staging, use the
  approved bursts recorded in `config.md`; an endpoint with none is
  `blocked`, not a reason to pause. Record the numbers used in `plan.md`.
  Never measure against production.
- Confirm a test identity for keyed limiters and a second identity if the
  limiter key needs to be distinguished.

## Coverage file

One row per endpoint or operation in these classes, whether or not it exists
in the target. Mark `not_applicable` only with affirmative evidence.

| Class | Examples |
|-------|----------|
| Authentication | login, signup, password reset, OTP or magic-link send and verify, token refresh |
| Messaging | email, SMS, push, invitations, notifications |
| Storage write | upload, presigned-URL issuance, multipart init, copy, import |
| Storage read | public object domains, signed download URLs, listing, thumbnails |
| Expensive compute | search, autocomplete, export, report or PDF generation, image or video transform, AI or LLM calls, geocoding, scraping |
| Billed invocation | serverless or edge functions, container endpoints that scale per request, third-party API proxies |
| Data volume | list endpoints with `limit` or `page_size`, GraphQL batch and depth, bulk operations, webhooks that fan out |
| State creation | records a user can create without bound: posts, comments, projects, API keys, sessions |

For each row record: where a limiter exists (edge rule, middleware, provider
setting, none), its key (IP, user, API key, none), body or size caps, quotas,
and the evidence reference.

## Candidate generation

Source: for each row trace the handler and its middleware chain. A route is
a candidate when the chain has no limiter, when the limiter keys only on IP
behind a proxy that does not forward the client address, when the store is
in-memory on a multi-instance deployment, when a body-size or file-size cap is
absent, when pagination has no maximum, or when a billed call happens before
authentication or before the limiter. Use `ensphere scan` categories and the
checklist "Look for" lines for the stack's idioms.

Live target: for each inventoried endpoint in the classes above, the candidate
is "no throttling response is observed within the approved burst".

Platform: for each billing-exposed service, check the provider-side controls
from Session 07 facts: Cloudflare rate-limiting rules and Bot Fight Mode,
Supabase auth rate limits and spend cap, Vercel firewall, cloud budget alerts,
function concurrency limits, R2 or S3 lifecycle and public-access state.

## Controlled validation

Rate limiting:

1. Baseline: one normal request with the test identity; record status and
   the `RateLimit-*`, `X-RateLimit-*`, `Retry-After`, `cf-ray`, and
   `cf-cache-status` headers.
2. Probe: `ensphere verify ratelimit` with the approved `--burst-count` and
   `--window-sec`. Read `first_throttle_at`, status codes, and captured
   headers per round.
3. Control: repeat the same burst with a second identity or API key to learn
   the limiter key, and with a request that should never be limited (a static
   asset or health endpoint) to separate throttling from general instability.
4. Stop at the first 429 or 503, at any error spike, or at the approved count.

Size and volume limits:

- Pagination: `ensphere verify limits --technique pagination` with an
  approved list of values; record returned item counts and body bytes per
  value. A count that tracks the requested value with no ceiling is the
  fact.
- Upload size: `ensphere verify limits --technique upload_size` with two or
  three approved sizes against a staging bucket or endpoint; record
  acceptance per size. Clean up uploaded objects and record the cleanup.
- Response size: record bytes for export and report endpoints at baseline;
  compare with the largest approved parameter value.
- GraphQL: `ensphere verify graphql --technique batch_query` with at most the
  approved batch size; record whether batching is accepted.

Storage abuse:

- Presigned URLs: read the issuing code for TTL, content-length range,
  content-type, and key-prefix constraints; record each as present or absent.
- Public read: with an operator-supplied canary object, record whether the
  public domain serves it without auth and whether cache or WAF rules exist in
  front of it.
- Listing: record whether any endpoint or bucket setting allows listing.

Interpretation: distinguish an edge limiter (Cloudflare headers, 429 with
`cf-ray`) from an origin limiter, a limiter keyed on IP from one keyed on
user, a hard cap from a soft warning, and instability from throttling. A
missing throttle within the approved burst is a measurement, not proof of an
unlimited endpoint; the source review or platform facts supply the rest.

## Reporting missing controls

Each `missing_control` finding states:

- the endpoint or service and its class;
- what control is absent (limiter, key, cap, quota, budget alert);
- the observed facts (source citation, burst measurement, platform setting);
- who can trigger it (anonymous, any user, privileged);
- what it costs the owner (compute, storage, egress, third-party spend, lock-
  out of legitimate users);
- the fix for this stack, taken from the checklist "Fix" line and adapted:
  the middleware or rule, the key to use, the store for multi-instance
  deployments (Upstash Redis, Cloudflare KV or Durable Objects,
  Memorystore), the cap value to start with, and the provider-side setting.

Also report the controls found working under "tested defenses" with the exact
burst and key they were tested with.

## Stop rules

Stop when the approved request count is reached, on the first throttle or
error spike, when the next step would create load or cost for the owner, or
when the claim is resolved. Never increase burst counts to "find the real
limit", distribute sources, rotate identities to evade a limiter, or upload
more than the approved sizes.

## Report

Write `08.5-abuse/report.md` with the `coverage.yaml` summary, approved limits used,
existing controls and their measured behavior, missing-control findings with
fixes, storage facts, platform-side settings, unresolved rows and missing
inputs, cleanup record, and evidence index.
